# 제조 공정 품질 불량 예측 서비스 구현 계획

## 1. 프로젝트 개요

### 목적

사출 공정 데이터를 이용해 CN7과 RG3 제품의 불량 가능성을 예측하고, 불량 가능성이 높은 제품을 작업자가 우선 검사할 수 있도록 지원하는 웹 대시보드를 구현한다.

대시보드에서는 다음 업무가 하나의 흐름으로 이어지도록 한다.

- 공정 데이터 수신 및 모니터링
- 제품별 불량확률 예측
- 작업자가 설정한 Threshold에 따른 검사 대상 선정
- 검사 시작, 실제 결과 및 조치 내용 기록
- 작업자와 품질 관리자 권한 구분
- 예측 이력과 검사 이력을 이용한 운영 성능 확인

### 구현 범위

프로젝트에서는 실제 설비와 연결하지 않고 기존 unlabeled 데이터를 생산시간 순서대로 재생해 실시간 데이터 수신을 구현한다. 전체 부품 데이터를 수신하되 현재 모델이 학습한 CN7과 RG3만 예측한다.

실제 공장 적용 시 데이터 재생 모듈을 센서, PLC, MES, 데이터베이스 또는 메시지 수신 방식으로 교체할 수 있도록 예측 기능과 화면 기능을 분리한다.

## 4. 데이터 정의

### 원본 unlabeled 데이터

unlabeled 데이터에는 제품 식별정보, 설비정보, 공정 측정값과 `ERR_FACT_QTY`가 포함되며 개별 제품의 `PassOrFail`과 `Reason`은 없다.

| 구분 | 변수 |
|---|---|
| 식별정보 | `_id`, `TimeStamp`, `PART_FACT_PLAN_DATE`, `PART_FACT_SERIAL` |
| 제품정보 | `PART_NO`, `PART_NAME` |
| 설비정보 | `EQUIP_CD`, `EQUIP_NAME` |
| 참고정보 | `ERR_FACT_QTY` |
| 공정시간 | `Injection_Time`, `Filling_Time`, `Plasticizing_Time`, `Cycle_Time`, `Clamp_Close_Time` |
| 위치 | `Cushion_Position`, `Switch_Over_Position`, `Plasticizing_Position`, `Clamp_Open_Position` |
| 속도 | `Max_Injection_Speed`, `Max_Screw_RPM`, `Average_Screw_RPM` |
| 압력 | `Max_Injection_Pressure`, `Max_Switch_Over_Pressure`, `Max_Back_Pressure`, `Average_Back_Pressure` |
| 온도 | `Barrel_Temperature_1~7`, `Hopper_Temperature`, `Mold_Temperature_1~12` |

`Unnamed: 0`이 존재하면 CSV 저장 과정에서 생성된 인덱스 열로 보고 제거한다.

### `Average_Screw_RPM` 기록 스케일 처리 (2026-09-09 확인)

`Average_Screw_RPM`과 `Max_Screw_RPM`은 컬럼명이 RPM이지만 **실제 단위는 둘 다 mm/s**다. 같은 물리량의 평균과 최대이므로 `Average ≤ Max`가 성립해야 한다.

`Average_Screw_RPM`이 기간에 따라 10배 스케일로 기록돼 있다.

| 데이터 | 값 범위 | 상태 |
| --- | --- | --- |
| labeled 2020-10-29 ~ 11-06 (2,209건) | 29.0 ~ 29.4 | 정상 (`Average/Max` 비율 0.95) |
| labeled 2020-10-16 ~ 10-27 (3,021건) | 290.4 ~ 293.9 | **10배로 기록** (비율 9.48) |
| unlabeled CN7/RG3 (71,091건) | 196.5 ~ 379.7 | **전 구간 10배로 기록** |
| unlabeled CN7/RG3 (53,940건) | 0.0 | **결측으로 추정** |

10으로 나누면 `Max_Screw_RPM`과 정합해 모순 행이 0이 된다(labeled 3,021건 → 0건, unlabeled 71,091건 → 0건).

예측 서버는 다음을 수행한다.

- **`Average_Screw_RPM`이 100을 넘으면 10으로 나눈다.** unlabeled는 대부분 이 경우에 해당하므로 보정 없이 예측하면 학습 분포와 10배 어긋난 값이 입력된다.
- `Average_Screw_RPM`이 0이면 결측으로 처리하고 해당 제품은 예측 결과에 `입력 이상`을 함께 반환한다. 확률을 그대로 신뢰하지 않는다는 것을 화면에 알린다.
- 보정 후에도 `Average > Max`인 행은 입력 이상으로 기록한다.
- 현재 저장된 모델은 보정 전 값으로 학습됐다. 성능 차이는 없으므로(`ANALYSIS_RESULTS.md` 11절) 재학습 시점에 학습 전처리에도 같은 보정을 넣어 학습과 서빙을 일치시킨다.

### 센서 데이터 결측 (2026-09-09 확인)

unlabeled CN7/RG3 125,031건 중 **53,940건(43.1%)에서 6개 변수가 동시에 0**이다. 수집 채널이 끊긴 것으로 보이며, 0은 물리적으로 불가능한 값이다(배럴온도 0℃, 금형온도 0℃, 배압 0). labeled 데이터에는 이 변수들이 0인 행이 없다.

동시에 0이 되는 변수: `Max_Screw_RPM`, `Average_Screw_RPM`, `Average_Back_Pressure`, `Barrel_Temperature_1`, `Mold_Temperature_3`, `Mold_Temperature_4`

- 이 중 `Mold_Temperature_4`(중요도 0.072), `Average_Back_Pressure`(0.062), `Mold_Temperature_3`(0.061)은 상위 중요도 변수다. 합쳐서 전체의 약 19%다.
- 6개가 항상 함께 0이므로 한 변수만 제외해도 해결되지 않는다.
- 중앙값 대체는 하지 않는다. 상위 중요도 변수 3개를 상수로 채우면 확률이 왜곡되고, 그 조건의 성능을 검증한 적이 없다.

**결측 행은 예측하지 않고 `데이터 결측` 상태로 표시한다.** 검사 큐에 올리지 않는다. 결측을 숨기지 않고 화면에 드러내는 것 자체가 기능이며, 결측률이 급증하면 수집 시스템 점검 신호가 된다.

여력이 생기면 결측된 6개를 제외한 18개 변수 전용 모델을 별도로 학습해 결측 행에 적용한다. 이 경우 성능을 04_6과 같은 프로토콜로 따로 측정한다.

### 학습에 없는 품명

unlabeled CN7/RG3 125,031건 중 **35,007건(28.0%)이 학습에 없는 품명**이다.

- `RG3 MLD'G-RR GLS LWR CVR`
- `RG3 MLD'G-RR GLS LWR CVR ASS'Y`
- `RG3 STRIP-RR GLS LWR CVR`

이 품명들의 `Part` 값은 `RG3VR`, `RG3SY` 등이 되어 학습 범주(`CN7LH`, `CN7RH`, `RG3LH`, `RG3RH`)에 없다. 더미 변수를 만들면 세 컬럼이 모두 0이 되는데, 이는 기준 범주인 **`CN7LH`와 같은 입력이 되어 조용히 잘못된 예측을 만든다.**

따라서 `PART_NAME`이 CN7 또는 RG3으로 시작하는 것만으로 예측 대상을 정하지 않는다. **`Part` 값이 학습 범주 4종에 속하는지 확인하고, 아니면 `모델 지원 대상 아님`으로 처리한다.**

### 모델 지원 대상

- 모델 예측 대상: `PART_NAME`이 CN7 또는 RG3로 시작하는 데이터
- 다른 부품: 데이터를 수신하되 예측하지 않고 `모델 지원 대상 아님`으로 처리
- `ERR_FACT_QTY` 값과 관계없이 CN7과 RG3의 전체 작업시간대를 사용

```python
supported_mask = data["PART_NAME"].str.startswith(
    ("CN7", "RG3"),
    na=False
)

prediction_data = data.loc[supported_mask].copy()
unsupported_data = data.loc[~supported_mask].copy()
```

### Part 파생변수

CN7, RG3 제품군과 LH, RH 방향을 구분하기 위해 `Part`를 생성한다.

```python
prediction_data["Part"] = (
    prediction_data["PART_NAME"].str[:3]
    + prediction_data["PART_NAME"].str[-2:]
)
```

예상 범주는 `CN7LH`, `CN7RH`, `RG3LH`, `RG3RH`이며 최종 예측 전 학습 데이터에 실제로 존재한 범주인지 확인한다.

### 모델 입력에서 제외하는 변수

- `_id`, `TimeStamp`
- `PART_FACT_PLAN_DATE`, `PART_FACT_SERIAL`
- `PART_NO`, `PART_NAME`
- `EQUIP_CD`, `EQUIP_NAME`
- `ERR_FACT_QTY`
- `PassOrFail`, `Reason`
- 학습 과정에서 삭제한 공정 변수

모델에는 학습 당시 저장한 `feature_cols`와 동일한 변수명과 순서로 입력한다.

### 데이터 역할 구분

| 구분 | 사용 정보 |
|---|---|
| 모델 입력 | 학습에 사용한 공정 변수와 `Part` |
| 화면 식별정보 | `_id`, `TimeStamp`, `PART_NO`, `PART_NAME` |
| 화면 설비정보 | `EQUIP_CD`, `EQUIP_NAME` |
| 참고정보 | `ERR_FACT_QTY` |
| 모델 출력 | 불량확률, 예측 라벨, 적용 Threshold, 모델 버전 |
| 검사 후 입력 | 실제 결과, 불량 유형, 점검 항목, 조치 내용 |

`ERR_FACT_QTY`는 여러 행에 같은 값이 반복될 수 있으므로 제품별 실제 불량으로 해석하거나 단순 합산하지 않는다. 정확한 집계 단위가 확인된 경우에만 작업지시 또는 시간대 참고지표로 사용한다.

### 같은 생산시각의 LH와 RH

동일 `TimeStamp`에 LH와 RH 제품이 함께 존재하고 공정값을 공유할 수 있다. 공정값이 같더라도 서로 다른 제품이므로 중복 제거하지 않는다.

- 제품과 검사 업무의 기준 키: `_id`
- 같은 시간의 LH와 RH는 각각 별도 예측 및 검사 상태를 가짐

## 5. 모델 적용 계획

### 기본 모델

최초 구현은 현재 확보한 머신러닝 분류 모델을 사용한다.

```text
공정 데이터
→ 입력값 검증
→ 전처리
→ 머신러닝 모델
→ 불량확률
→ Threshold 적용
→ 정상 또는 불량 위험
```

저장할 객체는 다음과 같다.

- 최종 분류 모델 또는 Pipeline
- 전처리 객체
- 학습 변수명과 순서
- 범주형 인코딩 정보
- 모델 버전
- 권장 Threshold
- Threshold별 검증 성능표

SMOTE는 학습 데이터에만 적용하고 실시간 예측에는 적용하지 않는다.

### 확정된 최종 모델 (2026-09-09)

`06_Final_Model.ipynb`에서 전체 5,230건으로 학습해 저장했다. 상세 근거는 `ANALYSIS_RESULTS.md`에 있다.

| 항목 | 값 |
| --- | --- |
| 모델 | `Pipeline(StandardScaler, RandomForestClassifier)` |
| 파라미터 | `n_estimators=300, max_depth=20, min_samples_split=2, min_samples_leaf=4, class_weight='balanced', random_state=0` |
| 입력 변수 | 26개 (공정 변수 23개 + `Part` 더미 3개, `Clamp_Open_Position` 제외) |
| 모델 버전 | `v1.1.0` |
| 성능 | Average Precision 0.3931 ± 0.1107 (5-fold × 3반복, 기록 오류 보정 후, **같은 기간 교차검증 기준**) |

저장 파일은 다음과 같다.

- `models/final_rf_part_balanced.pkl`: 전처리를 포함한 Pipeline. 원본 값을 그대로 넣으면 되고 별도 스케일링이 필요 없다.
- `models/final_feature_columns.pkl`: 학습 변수명과 순서. 예측 시 이 순서로 정렬한다.
- `models/final_model_meta.json`: 모델 버전, 파라미터, 범주형 인코딩 규칙, 권장 Threshold, 검사 물량별 성능표

학습 전처리는 `utils/preprocessing.py`의 `apply_data_corrections`를 거친다. 예측 서버도 같은 함수를 사용해야 한다. `Part` 인코딩 규칙은 `PART_NAME[:3] + PART_NAME[-2:]`이며, 더미 컬럼은 `Part_CN7RH`, `Part_RG3LH`, `Part_RG3RH` 세 개다. `drop_first=True`를 사용했으므로 **CN7LH는 세 더미가 모두 0인 상태**로 표현한다.

SMOTE는 최종 모델에 포함되지 않는다. `class_weight='balanced'`로 불균형을 처리한다.

### 오토인코더 추가 여부: 미적용으로 확정 (2026-09-09)

`04_6_AutoEncoder_CV_Validation.ipynb`에서 5-fold × 3반복으로 같은 fold 짝비교를 수행한 결과 적용하지 않기로 확정했다.

- Average Precision은 모델에 따라 +0.004 ~ +0.034 올랐으나, 효과 크기가 fold 표준편차(0.10 ~ 0.12)보다 훨씬 작다.
- **검사 물량 5 ~ 10% 구간에서는 일관된 이득이 없다.** Bagging은 Recall@10%가 0.05 내려갔고, RandomForest Balanced는 0.017 내려갔다.
- 따라서 예측 서버는 오토인코더와 MinMaxScaler를 유지하지 않는다. `final_rf_part_balanced.pkl`과 `final_feature_columns.pkl`만 사용한다.

이후 오토인코더를 다시 적용하게 되면 React와 Supabase 구조는 변경하지 않고 FastAPI 내부 예측 모듈만 교체한다. 모델이 바뀌면 해당 모델에 맞는 Threshold와 검증 성능표도 다시 확정한다.

## 7. Threshold 운영

### 기본 원칙

- 모델은 Threshold와 관계없이 불량확률을 계산한다.
- Threshold는 불량 위험으로 분류할 기준만 변경한다.
- 작업자는 품질 관리자가 설정한 허용 범위 내에서 조절한다.
- Threshold를 낮추면 검사 대상과 Recall이 증가할 가능성이 있지만 양품 오탐도 증가한다.
- Threshold를 높이면 검사 대상과 오탐은 감소하지만 불량 미탐 가능성이 증가한다.
- **Threshold는 검사 물량에서 역산해 정한다.** 검사 인력이 하루에 감당할 물량을 먼저 정하고, 그 물량에 해당하는 Threshold를 아래 표에서 선택한다.

### 확정된 운영점 (2026-09-09)

`05_Operating_Point.ipynb`에서 5-fold × 3반복 OOF 확률로 계산했다. 하루 평균 생산 402건, 하루 평균 불량 4.62건 기준이다.

| 검사 물량 | Threshold | 하루 검사 건수 | 불량 검출률 | 하루 검출 불량 | 하루 헛검사 | Lift |
| --- | --- | --- | --- | --- | --- | --- |
| 1% | 0.639 | 4건 | 32.2% | 1.49건 | 2.5건 | 32.4배 |
| 3% | 0.422 | 12건 | 45.0% | 2.08건 | 10.0건 | 15.0배 |
| 5% | 0.316 | 20건 | 53.3% | 2.46건 | 17.7건 | 10.6배 |
| 7% | 0.250 | 28건 | 68.3% | 3.15건 | 25.0건 | 9.8배 |
| **10% (권장)** | **0.163** | **40건** | **78.9%** | **3.64건** | **36.6건** | **7.9배** |
| 15% | 0.079 | 60건 | 86.1% | 3.97건 | 56.4건 | 5.7배 |
| 20% | 0.035 | 80건 | 93.9% | 4.33건 | 76.1건 | 4.7배 |

- **기본값은 Threshold 0.163**로 한다. 하루 약 40건을 검사해 불량의 약 79%를 잡는 지점이다. 시연 구간에서 실제 알람률은 11.06%였다.
- Lift는 같은 건수를 무작위로 검사했을 때 대비 몇 배 효율인지를 뜻한다. 검사 물량을 늘리면 검출률은 오르지만 Lift는 떨어진다.
- Threshold의 반복 간 표준편차는 0.002 ~ 0.009로 안정적이므로 고정값 운영이 가능하다. 다만 일별 생산량 편차가 크므로(최소 1건, 최대 926건) 알람 건수는 날마다 달라진다.
- 검사 물량 15% 이상 구간의 높은 검출률은 모델 성능이 아니라 검사 물량을 늘린 결과다. 허용 범위 하한을 Threshold 0.079(15%)로 두는 것을 권장한다.

### 운영 방식 결정 기록 (2026-09-09)

**결정: 실시간 Threshold 방식을 채택하고, 인력 초과를 막기 위해 물량 상한과 대기 큐를 함께 둔다.**

분석에서 성능을 검사 물량 기준(Recall@k)으로 측정했으므로, 운영도 "확률 상위 k%만 검사"로 할 수 있는지 검토했다. 세 가지 대안을 비교했다.

| 항목 | A. 물량 방식 (배치 Top-k) | B. Threshold 방식 (실시간) | C. Threshold + 물량 상한 (채택) |
| --- | --- | --- | --- |
| 판정 시점 | 하루 또는 교대조 마감 후 | 제품이 나오는 즉시 | 즉시 |
| 검사 물량 | 고정 (하루 40건) | 변동 (하루 0 ~ 177건) | 상한까지 즉시, 초과분은 대기 큐 |
| 위험 구간 대응 | 불가 (물량이 고정이라 몰린 구간을 더 못 봄) | 자동으로 검사가 몰림 | 자동 + 상한 초과 시 공정 점검 전환 |
| 인력 계획 | 쉬움 | 어려움 | 상한으로 관리 가능 |
| 조치 가능성 | 낮음 (이미 출하됨) | 높음 | 높음 |
| 구현 난이도 | 중간 (마감 시점 배치 작업 필요) | 낮음 | 낮음 (상한 카운터와 큐 정렬만 추가) |

#### 채택 근거

1. **불량이 에피소드로 발생한다.** 13일 중 6일에만 불량이 있었고, 불량이 난 시간대는 59시간 중 15시간이며 한 시간에 최대 17건이 나왔다. 개별 제품이 독립적으로 불량인 것이 아니라 공정이 흔들린 구간에서 몰려 나온다. 이런 분포에서는 검사 자원도 그 구간에 몰려야 한다. Threshold 방식은 이것이 자동으로 된다.
2. **같은 검출을 더 적은 검사로 달성한 사례가 있다.** 10월 27일은 알람 15건으로 불량 10건을 모두 잡았다. 물량 방식이면 같은 날 63건(628건의 10%)을 검사해야 했다. 반대로 불량이 없던 날은 알람이 0 ~ 4건이라 인력을 쓰지 않는다.
3. **총량으로는 물량 방식과 같다.** Threshold 0.165를 13일 전체에 적용하면 알람 535건으로 전체의 10.2%이고 불량 48/60건(80.0%)을 검출한다. 물량 기준 Recall@10%(77.2%)와 같은 수준이며 오히려 조금 높다. **즉 물량 예측 가능성을 잃는 대신 얻는 손실이 없다.**
4. **조치 가능성.** 사출 사이클이 약 60초이므로 즉시 판정이 나오면 해당 제품을 라인에서 분리할 수 있다. 마감 후 상위 40건을 고르면 그 제품은 이미 포장되었거나 출하된 상태다.

#### 물량 방식을 기각한 근거

- 판정이 늦어 조치가 불가능하다. 검사 대상을 골라도 제품 추적이 어렵다.
- 불량이 없는 날(13일 중 7일)에도 40건씩 검사해 인력을 낭비한다.
- 불량이 몰린 날(10월 22일 불량 15건)에는 40건으로 부족하다.
- `plan.md` 1절의 목적("불량 가능성이 높은 제품을 작업자가 우선 검사")과 실시간 모니터링 화면 구조에 맞지 않는다.

#### 채택에 따라 감수하는 위험과 완화책

| 위험 | 완화책 |
| --- | --- |
| 알람 물량이 날마다 크게 변동 (0 ~ 177건) | 교대조 검사 상한 + 확률 내림차순 대기 큐 |
| 시간당 알람이 인력을 초과 (90분위 30건, 최대 82건) | 위험 구간 전환 규칙으로 개별 검사에서 공정 점검으로 전환 |
| 공정 드리프트로 확률 분포가 이동 (일별 90분위 0.002 ~ 0.668) | 2단계에서 분위수 기반 Threshold 자동 재조정, 안전 범위 0.079 ~ 0.639 |
| 모델이 헤매는 날 존재 (10월 23일: 알람 139건, 검출 4/10) | `inspection_reason`별 집계로 사후 확인, 표본검사로 열화 감시 |

#### 재검토 조건

- 검사 인력이 고정 물량 계약이어서 일별 변동을 흡수할 수 없는 경우
- 검사가 라인 밖 별도 공정에서 배치로만 가능한 경우
- 대기 큐가 계속 소진되지 않아 알람이 실질적으로 버려지는 경우

- 13일 합계는 알람 535건(전체의 10.2%), 불량 검출 48/60건(80.0%)이다.

- **교대조 검사 상한**을 설정한다(예: 8시간 교대당 15건). 품질 관리자가 설정한다.
- 상한을 넘는 알람은 버리지 않고 `검사 대기` 큐에 **불량확률 내림차순**으로 쌓는다. 인력이 비면 확률이 높은 순으로 `검사 대기`에서 꺼낸다.
- 큐 길이와 대기 시간을 화면에 표시한다. 큐가 계속 길어지면 Threshold를 올리거나 인력을 늘리는 판단 근거가 된다.

### 위험 구간 전환 규칙

시간당 알람이 상한을 크게 넘으면 개별 제품 검사로는 대응할 수 없다. 실제로 알람이 몰린 시간대는 공정 자체가 흔들린 구간이었다.

- 시간당 알람이 **30건(관측 90분위)을 넘으면** 개별 제품 검사 대신 **공정 점검 알림**으로 전환한다.
- 점검 항목: 금형 온도, 사출압, 보압 전환 위치, 원료 로트 변경 여부, 직전 금형 교체 시점
- 이 상태에서는 해당 구간 제품을 일괄 보류하고, 공정 조치 후 재개하는 것이 개별 검사보다 효과적이다.
- 전환 이력(발생 시각, 알람 수, 조치 내용, 해제 시각)을 저장한다.

### 2단계 개선: Threshold 자동 재조정 (선택)

금형 교체나 원료 로트 변경으로 확률 분포가 이동하면 고정 Threshold의 알람 물량이 달라진다. 실제로 일별 확률 90분위가 0.002 ~ 0.668까지 움직였다.

- 최근 일정 물량(예: 최근 3,000건)의 확률 분포에서 **90분위수를 Threshold로 자동 갱신**하면 알람 물량이 대략 10%로 유지된다.
- 자동 갱신값은 **0.079 ~ 0.639 범위**(검사 물량 15% ~ 1%)로 제한해 이상값으로 튀는 것을 막는다. 이 표는 기록 오류 보정 후 기준이다.
- 갱신 이력을 수동 변경과 같은 형식으로 저장하고, 갱신 폭이 클 때는 품질 관리자에게 알린다.
- 1차 구현에서는 고정 Threshold 0.163으로 운영하고, 이 기능은 예측 이력이 쌓인 뒤 적용한다.

### 화면 표시

- 현재 Threshold
- 예상 검사 대상 수와 비율
- 검증 데이터 기준 예상 Precision과 Recall
- 성능 수치의 기준 데이터와 모델 버전
- **해당 Threshold의 예상 검출률과 하루 검사 건수**를 위 표 기준으로 함께 표시한다. 예: "Threshold 0.163 · 하루 약 40건 검사 · 불량 약 79% 검출 예상"
- 성능 수치의 출처는 "라벨 데이터 5,230건(불량 60건), 5-fold × 3반복 교차검증"으로 표기하고, 모델 버전 `v1.1.0`을 함께 보여준다.
- **성능 수치에 "같은 기간 교차검증 기준"이라는 단서를 함께 표시한다.** 생산일 단위로 분할해 새로운 날에 적용하면 성능이 크게 떨어진다(AP 0.39 → 0.02, `ANALYSIS_RESULTS.md` 11절). 운영 실제 성능은 표본검사로 확인한다.
- **오늘 결측률과 모델 지원 대상 아님 비율**을 표시한다. 결측이 급증하면 수집 시스템 점검 신호이며, 예측 가능한 물량이 줄었다는 뜻이므로 검사 계획에도 영향을 준다.
- **교대조 검사 상한, 오늘 누적 검사 수, 검사 대기 큐 길이**를 함께 표시한다. 알람 물량이 날마다 크게 변하므로 현재 부하를 보여주는 것이 Threshold 값 자체보다 중요하다.

실시간 unlabeled 데이터에는 개별 제품 정답이 없으므로 Precision과 Recall은 검증 데이터 기준 예상값으로 표시한다. 운영 성능은 검사 결과가 입력된 제품만으로 별도 계산한다.

### 적용과 이력

- 이미 검사 대기 또는 검사 중인 제품은 Threshold 변경 후에도 목록에서 제거하지 않는다.
- 변경 이후 수신되는 제품부터 새로운 Threshold를 적용한다.
- 시연 모드에서는 비교를 위해 현재 데이터 전체를 즉시 재분류할 수 있다.
- 변경 전 값, 변경 후 값, 변경자, 변경시간, 변경 사유를 저장한다.

## 9. 검사 업무 기능

### 검사 시작

1. 선택한 제품의 `_id`와 현재 상태를 확인한다.
2. 검사 상태를 `검사 대기`에서 `검사 중`으로 변경한다.
3. 로그인한 작업자 ID와 이름을 기록한다.
4. 검사 시작 시간을 저장한다.
5. 다른 작업자의 중복 검사를 방지한다.

### 결과 입력

검사 시작 후 결과 입력 기능을 활성화하고 다음 항목을 받는다.

- 실제 결과: 정상 또는 불량
- 불량 유형
- 확인한 공정 또는 설비
- 조치 내용
- 추가 검사 필요 여부
- 검사 완료 시간

불량을 선택하면 불량 유형을 필수 입력으로 설정한다.

| 모델 예측 | 실제 검사 | 평가 결과 |
|---|---|---|
| 불량 위험 | 불량 | TP, 불량 탐지 |
| 불량 위험 | 정상 | FP, 양품 오탐 |
| 정상 | 불량 | FN, 불량 미탐 |
| 정상 | 정상 | TN, 정상 판정 |

불량 위험 제품만 검사하면 TP와 FP만 확인할 수 있다. FN과 TN을 계산하려면 정상 예측 제품에 대한 표본검사 또는 기존 품질검사 결과가 필요하다.

### 표본검사 설계

**목적은 Recall의 정밀 측정이 아니라 모델 열화 감시다.** 알람 제품만 검사하면 Precision은 매일 계산되지만 놓친 불량(FN)은 관측되지 않으므로, 정상 예측 구간의 불량률이 올라가는지 감시한다.

기준값은 다음과 같다. Threshold 0.165(검사 물량 10%, 검출률 77.2%) 운영 시 하루 평균 생산 402건, 불량 4.62건이므로

- 알람 구간: 약 40건, 불량 3.56건 검출
- 정상 예측 구간: 약 362건, **놓친 불량 1.06건 → 불량률 약 0.29%**

이 0.29%가 감시 기준선이다. 표본검사에서 관측되는 불량률이 이보다 뚜렷하게 높아지면 모델이 열화된 것으로 본다.

우선순위는 다음 순서로 둔다.

1. **기존 품질검사 결과 연계 (최우선).** 현장에 정기 샘플링 검사나 후공정 검사가 이미 있으면 그 결과를 `inspections`에 입력받는다. 별도 표본검사보다 표본 수가 크고 추가 인력이 들지 않는다.
2. **정상 예측 제품 무작위 표본검사.** 1번이 없을 때 정상 예측 제품의 **5%를 무작위 추출**한다(하루 약 18건). 확률이 높은 순이 아니라 반드시 무작위로 뽑아야 편향이 생기지 않는다.
3. **고객 클레임과 후공정 불량 역추적.** 발생 시 해당 `_id`의 예측 확률을 조회해 FN으로 기록한다.

표본검사 표본 수의 한계를 명시한다.

- 5% 표본(하루 18건)이면 월 20영업일 누적 약 360건이고, 기준선 0.29%에서 기대 관측 불량은 **월 1건 수준**이다.
- 따라서 월 단위로 누적해서 판단하며, **모델이 2배 이상 나빠지는 수준만 감지할 수 있다.** 월 누적 표본에서 불량 4건 이상이 관측되면 열화로 판단하고 재학습을 검토한다(기대값 1건 기준 포아송 상위 2% 수준).
- Recall을 정밀하게 추정하려면 4,000건 이상의 표본이 필요하므로 이 시스템에서는 목표로 삼지 않는다. 대신 월 1회 전수 검사일을 운영할 수 있다면 그날 데이터로 Recall을 직접 계산한다.

화면과 저장 항목은 다음과 같다.

- 작업자 화면에 표본검사 대상을 `표본검사` 배지로 별도 표시한다. 불량 위험 알람과 구분해야 작업자가 "왜 정상인데 검사하나"를 혼동하지 않는다.
- 관리자 화면에 월 누적 표본 수, 표본 불량률, 기준선 0.29%, 열화 판단 결과를 표시한다.
- `inspections`에 검사 사유를 저장한다: `알람`(Threshold 초과) / `표본`(무작위 표본검사) / `클레임`(역추적) / `대기큐`(상한 초과 후 처리).
- 운영 성능 계산 시 **검사 사유별로 분리한다.** 알람 검사 결과로 Precision을, 표본 검사 결과로 정상 구간 불량률을 계산한다. 두 집단을 섞으면 Precision이 낮게 왜곡된다.

## 11. 실시간 시연 방식

### 재생 구간 확정: 2020-10-18 ~ 10-22 (2026-09-09 결정)

unlabeled 전 구간을 대상으로 결측률, 지원 품목 비율, 알람 발생률을 계산해 선정했다.

| 구간 | 행 수 | 결측률 | 예측 대상 | 알람 | 알람률 | lot 불량 |
| --- | --- | --- | --- | --- | --- | --- |
| **2020-10-18 ~ 10-22 (채택)** | 13,666 | **0.0%** | 13,666 | 1,512 | **11.1%** | 396 |
| 2020-10-19 ~ 10-23 | 11,054 | 0.0% | 11,054 | 1,356 | 12.3% | 360 |
| 2020-04-02 ~ 04-06 | 1,315 | 0.0% | 1,315 | 1,315 | **100%** | 798 |
| 2020-06-23 ~ 07-03 | 3,830 | 0.0% | 746 | 745 | **99.9%** | 365 |
| 2020-10-07 ~ 10-13 | 3,246 | 0.0% | 1,384 | 24 | **1.7%** | 89 |

채택 근거는 다음과 같다.

1. **결측이 0%이고 전량이 학습된 품명 4종이다.** 13,666행 모두 예측 가능하다.
2. **알람률 11.1%가 확정 운영점(검사 물량 10%, Threshold 0.163)에 근접한다.** 7절 설계가 시연에서 거의 그대로 재현된다. 1%p 차이는 학습 기간과 시연 기간의 분포 차이에서 온다.
3. **학습 기간(2020-10-16 ~ 11-06)과 인접해 분포 차이가 가장 작다.** 4월 초, 6월 하순, 7월 구간은 알람률이 98 ~ 100%로 모델이 전량 알람을 내고, 10-07 구간은 1.7%로 거의 알람이 없다. 학습 기간과 멀어질수록 분포가 달라지기 때문이며, 시연에 쓰면 "모든 제품이 불량 위험" 또는 "알람이 아예 없음"이 된다.
4. **시연 서사가 자연스럽다.** 일별 알람률이 10-18 ~ 10-20에 3.5 ~ 3.9%로 안정적이다가 10-21 20.0%, 10-22 24.2%로 올라간다. 초반 3일은 정상 운영, 후반 2일은 위험 구간 대응(7절 위험 구간 전환 규칙)을 보여줄 수 있다.
5. lot 불량이 396건 있어 실제 불량이 발생한 구간이다.

| 생산일 | 예측 대상 | 알람 | 알람률 |
| --- | --- | --- | --- |
| 10-18 | 2,878 | 111 | 3.9% |
| 10-19 | 2,879 | 110 | 3.8% |
| 10-20 | 2,446 | 86 | 3.5% |
| 10-21 | 2,761 | 552 | 20.0% |
| 10-22 | 2,702 | 653 | 24.2% |

하루 2,400 ~ 2,900건이므로 실제 생산 속도(약 60초/샷)보다 빠르게 재생해야 한다. 재생 속도는 시연 시간에 맞춰 조절한다.

### 재생 절차

1. unlabeled 데이터에서 불필요한 인덱스 열을 제거한다.
2. `TimeStamp`를 날짜시간형으로 변환한다.
3. 생산시간과 생산순번을 기준으로 정렬한다.
4. 데이터를 2초에서 5초 간격으로 한 행씩 재생한다.
5. `Part` 값이 학습 범주 4종에 속하고 센서 결측이 없으면 FastAPI에 예측을 요청한다.
6. 학습 범주에 없는 품명은 `모델 지원 대상 아님`, 센서 결측 행은 `데이터 결측`으로 기록한다.
7. 결과를 Supabase와 화면에 반영한다.
8. 같은 생산시각의 LH와 RH는 각각 별도 제품으로 처리한다.

시연 기능은 시작, 일시정지, 다음 제품, 초기화로 구성한다.

## 14. 완료 기준

- 사용자가 로그인하고 권한에 맞는 화면을 확인할 수 있다.
- 전체 데이터 중 CN7과 RG3만 모델 예측을 수행한다.
- 같은 생산시각의 LH와 RH를 서로 다른 제품으로 처리한다.
- FastAPI가 머신러닝 모델의 불량확률을 반환한다.
- 작업자가 허용 범위에서 Threshold를 조절할 수 있다.
- 예측 당시 Threshold와 모델 버전이 저장된다.
- 불량 위험 제품이 검사 대기 목록에 추가된다.
- 작업자가 검사 시작과 결과 입력을 완료할 수 있다.
- 로그인 작업자, 검사시간, 실제 결과와 조치 내용이 저장된다.
- 예측 이력과 검사 이력이 `_id`를 기준으로 연결된다.
- 모델 지원 대상 외 제품은 별도 상태로 표시된다.
- 모델 교체 시 React 화면을 수정하지 않고 FastAPI 예측 모듈을 교체할 수 있다.
