교대조 기능을 구현할 때 이 자리를 다시 쓴다.

## 2026-09-16 — 검증 성능표의 k 명시와 지원 제품 전체 품명 표시

### 문제

**1. `Recall@k`의 k가 화면 어디에도 없었다.** 검증 성능표는 k(검사 물량)를 고정해 "확률 상위 k%를 검사했다면"을 잰 값이고 Threshold는 그 k에 대응하는 확률 컷인데, 표의 첫 열이 Threshold였고 지표 이름은 `Recall@k`로 k가 빈칸이었다. Threshold 패널과 변경 모달도 마찬가지였다. k가 하나로 정해진 값이라는 오해를 부른다.

실제 운영은 반대다. `ANALYSIS_RESULTS.md` 7절에 기록한 대로 "확률 상위 k%만 검사"는 하루 물량이 다 나와야 순위를 매길 수 있어 실시간에 맞지 않으므로, 대시보드는 Threshold를 고정하고 검사 건수가 공정 상태에 따라 떠다니게 한다(라벨 13일 기준 하루 알람률 0.4% ~ 95.8%). 두 방식이 화면에서 구분되지 않으면 검증표의 「예상 검사 수 40건」을 오늘의 검사 계획으로 읽게 된다.

**2. 지원 제품이 모델 내부 범주 코드로만 표시됐다.** `CN7LH`는 `PART_NAME`의 앞 3글자 + 뒤 2글자를 붙인 학습용 범주이지 현장에서 부르는 이름이 아니다.

### 변경 내용

**검증 성능표**

- 열 순서를 바꿔 `검사 물량 (k)`를 첫 열로 올리고 `Threshold`를 두 번째로 내렸다. 기본 운영점 태그도 k 열에 붙는다.
- `Recall@k (예상 검출률)` 표기를 현재 운영점의 실제 k로 채운다. Threshold 패널과 변경 모달에서 `Recall@10%`처럼 보인다. 슬라이더를 움직이면 가장 가까운 운영점의 k를 따라간다.
- 표 아래에 한 줄을 추가했다. "k는 검사 물량입니다. 이 표는 k를 고정해 잰 값이고 Threshold는 그 k에 해당하던 확률 컷입니다. 실제 운영은 반대로 Threshold를 고정하므로 하루 검사 건수는 공정 상태에 따라 달라집니다."

**지원 제품**

- `settings.SUPPORTED_PART_NAMES`에 범주 → 전체 품명 매핑을 두고 `/model/info`가 내려준다. 학습 데이터와 시연 표본 모두 범주 하나당 품명이 정확히 하나씩이라(`nunique == 1`) 고정 매핑으로 뒀다.
- 화면은 전체 품명을 주 텍스트로, 범주 코드를 보조로 보여준다(`CN7 W/S SIDE MLD'G LH` / `모델 범주 CN7LH`).
- `part-grid`를 2열에서 1열로 바꿨다. 2열에서는 품명 끝이 잘리는데 하필 그 끝의 `LH`/`RH`가 좌우를 가르는 정보다.

## 2026-09-16 — 재생 위치 경합으로 같은 제품이 다시 재생되는 문제 수정

### 문제

재생이 도는 중에 초기화가 들어오면 수신 건수가 더 이상 늘지 않고, 이미 저장된 제품을 처음부터 다시 재생하는 상태가 됐다. 실제로 `received: 560`인데 `demo_cursor`가 4에서 22로 올라가는 상태를 관측했다. `record_id`가 기본키라 같은 제품을 다시 예측해도 행이 늘지 않고 덮어써지기 때문에 화면상 재생이 멈춘 것처럼 보인다.

### 변경 내용

- `Repository.reserve_demo_sequence(count, total)`를 추가했다. 읽기와 쓰기를 한 트랜잭션·한 락 안에서 처리하고 `(시작 위치, 실제 건수)`를 돌려준다. 표본 끝을 넘으면 남은 만큼만 준다.
- `advance_demo`는 예측 전에 구간을 먼저 예약하고, 끝에서 `set_state`로 커서를 쓰던 코드를 제거했다. 동시에 들어온 요청끼리 구간이 겹치지 않는다.

## 2026-09-16 — 불량확률 소수점 표기와 화면 수정 묶음

### 문제

1. **확률이 전부 `0%`로 보였다.** 예측 600건 중 22%가 정확히 `0.0000`이고 28%가 0.5% 미만인데, 표시 함수가 정수로 반올림해서 최근 수신 내역의 상당수가 구분 없이 `0%`로 뭉개졌다. 불량률 1.1% 데이터로 학습한 모델이라 값 자체는 정상이다.
2. **재학습 실행 패널의 버튼이 패널 밖으로 나갔다.** `.button.full`이 `width: 100%`인데 패널이 자식에게 좌우 여백 18px씩을 줘서 정확히 36px만큼 넘쳤다.
3. **검증 성능표의 「기본」 태그가 한 번도 뜨지 않았다.** `default_threshold`가 0.163이고 성능표 값은 0.1627이라 `===` 비교가 항상 거짓이었다. 확률을 소수점 1자리로 바꾸자 둘 다 `16.3%`로 보이면서 드러났다.
4. **자동 재생 중 버튼이 매초 깜빡였다.** `advance`가 1초마다 `setBusy(true) → false`를 반복해서 `disabled={busy}`가 걸린 버튼이 `opacity: .45`와 1을 오갔다. 검사 시작·결과 입력·다음·초기화가 모두 해당됐다.
5. **검사 중인 제품의 담당자를 알 수 없었다.** `worker_name`은 `inspections`에만 있는데 화면용 조회는 `predictions`만 읽었다.

### 변경 내용

**표기**

- `percentage()`의 기본 자릿수를 0에서 1로 바꿨다. 기준선인 Threshold도 0.163처럼 소수점을 쓰므로 같은 자릿수로 보여야 16.2%인 제품이 정상으로 판정된 것이 화면에서 납득된다. 비율 성격이라 정수가 맞는 「지원 처리율」과 「검사 물량」만 0을 명시적으로 넘긴다.
- Threshold 슬라이더의 큰 숫자, 검사 결과 입력 폼, 추이 차트의 `TH` 라벨도 소수점 1자리로 맞췄다. 슬라이더 step이 0.001이라 정수 표기로는 조작 결과가 보이지 않았다.
- 대기열 확률 칸을 92px에서 104px로 넓히고 숫자에 `min-width: 44px`와 우측 정렬을 줘서 막대 길이가 행마다 흔들리지 않게 했다.

**수정**

- `.retrain-panel .button.full`의 `width`를 `auto`로 풀었다. flex 컬럼의 stretch가 여백을 뺀 너비로 늘려준다. 같은 패턴을 전체에서 확인했고 모달의 `.detail-side` 버튼은 padding을 쓰므로 영향이 없다.
- 검증 성능표의 기본 운영점 판정을 `Math.abs(row.threshold - default) < 0.001`로 바꿨다.
- `advance`의 `silent`(자동 재생) 경로에서는 `busy`를 건드리지 않는다. 중복 실행은 원래 `busyRef`가 막고 있어 안전하다.

**검사 담당자 표시**

- 화면용 조회(`list_predictions`, `list_inspection_queue`, `get_prediction`, `search_predictions`)에 `inspections` LEFT JOIN을 걸어 `inspector`와 `inspection_started_at`을 내려준다. `search_predictions`는 양쪽에 `record_id`가 있어 모호해지므로 조건을 전부 `p.`로 한정했다.
- 검사 대기열·상세 모달·최근 수신 내역 세 곳에 담당자 이름을 표시한다. 상세의 업무 처리 안내문은 "박품질 담당으로 검사가 진행 중입니다 (12:51:20 시작)"로 바뀐다.

**용어**

- 「서빙 중」·「서빙 모델」을 「운영 중」·「운영 중인 모델」로 바꿨다. 탭 이름이 「모델 운영」이라 화면 용어를 맞췄다. 백엔드 주석의 "서빙"은 기술 용어라 유지한다.


## 2026-09-16 — 시연 시작 시드 560건과 자동 재학습 기준 5건 확정

### 문제

표본을 1,000건으로 늘린 뒤에도 빈 화면에서 시작하면 검사 대기열이 찰 때까지 오래 걸렸다. 위험 제품이 표본에 고르게 있지 않기 때문이다. 실측하면 1~100번째는 0건, 첫 위험이 164번째, 301~500번째는 200건 내리 0건이고, 501번째부터 500건에 83건이 몰려 있다.

자동 재학습 기준도 근거 없이 10건으로 잡혀 있었다.

### 변경 내용

**시드 560건** (`settings.DEMO_SEED_RECORDS`)

처음에 500으로 잡았으나 추이 차트가 최근 60건(441~500)을 그리는데 그 구간이 전부 위험 0건이라 차트가 바닥에 붙은 평평한 선으로 보였다. 560으로 옮긴 기준은 세 가지다.

| | 500 | 560 |
| --- | --- | --- |
| 검사 대기열 | 14건 | 21건 |
| 차트 중앙값 | 0.00% | 6.45% |
| 차트 위 위험 점 | 0개 | 7개 |
| 남은 재생 | 8분 20초 | 7분 20초 |

**자동 재학습 기준 5건** (`settings.AUTO_RETRAIN_MIN_LABELS`)

07_2(`ANALYSIS_RESULTS.md` 7-1)는 반영 지연이 **25분 이내 / 1시간~35시간 / 하루** 세 구간으로 갈리고 구간 안의 차이는 노이즈라고 측정했다. Threshold 0.163에서 검사 물량이 생산의 10%이므로 검사 1건은 생산 10샷이고 생산은 분당 약 2샷이다.

- 검사 5건 = 생산 50샷 = 약 25분 → 25분 이내 구간
- 검사 10건 = 생산 100샷 = 약 51분 → 1시간~35시간 구간

기존 10건은 성능이 좋은 구간을 벗어나 있었다. Threshold를 바꾸면 검사 물량 비율이 달라지므로 이 환산도 다시 해야 한다는 주석을 상수 위에 남겼다.

**07_2 근거표를 구간 단위로**

처음에는 50샷 행만 강조하고 「권장」 태그를 달았는데, 이는 "50샷이 최적"이라는 잘못된 읽기를 유도한다. 10샷 0.581 / 25샷 0.581 / 50샷 0.628은 사실상 같은 값이다. `band` 필드를 넣어 25분 이내 세 행을 함께 강조하고 태그를 「권장 구간」으로 바꿨다. 표 아래에 현재 자동 기준이 몇 샷·몇 분에 해당하는지 자동 계산해 표시한다.

### 실행 확인

초기화 → 수신 560 / 위험 21 / 대기 21, 차트 최근 60건에 threshold 초과 7점. 검사 5건째에 자동 재학습 v1.2.0 발동(학습 5,235건, 추가 5건). 시드 지점의 최근 60건에 위험 판정이 없으면 실패하는 테스트를 추가했다.


## 2026-09-16 — 예측을 건별에서 배치로 전환

### 문제

시드를 500건으로 올리자 초기화가 24.3초 걸렸다. 시연 중 초기화 버튼을 누르면 화면이 그만큼 멈춘다.

측정하니 21초가 예측이었다. 300트리 RandomForest에 1행짜리 DataFrame을 500번 넣으면 건당 42ms인데, 같은 500건을 한 번에 넣으면 0.052초다. **405배 차이**이며 모델 시간이 아니라 호출당 오버헤드다.

### 변경 내용

- `prediction.py`를 `prepare_record`(모델 호출 직전까지 판정)와 `apply_probability`(확률을 채워 결과 완성)로 나눴다. `prepare_record`는 `(결과, None)` 또는 `(골격, 입력행)`을 돌려준다. 앞은 모델을 부르지 않고 끝난 건(미지원 품명, 미학습 설비, 센서 결측)이다.
- `predict_records(records, threshold, model_version)`를 추가했다. 예측 가능한 행만 모아 `predict_proba`를 한 번만 호출한다. 개별 건의 `ValueError`는 그 자리에 담아 돌려주므로 한 건 때문에 재생이 멈추지 않는다.

이 데이터는 기능 발표를 위해 지원 제품 비중을 높인 `시연용 재구성 데이터`다. 제품 비율과 예측 결과 분포를 실제 공장의 생산 비율이나 불량률로 해석하지 않는다.

## 2026-09-09 — 검사 대기열 항목이 사라지는 문제 수정

### 현상

실시간 데이터가 계속 쌓이면 아직 검사를 시작하거나 완료하지 않은 제품이 검사 대기열에서 사라지는 문제가 있었다.

### 원인

검사 대기열을 별도 데이터로 조회하지 않고 최근 예측 목록에서 다시 계산하고 있었다.

- 프론트엔드는 최근 예측 60건만 API에서 조회했다.
- 검사 대기열도 이 60건 안에서 `검사 대기`, `검사 중` 상태를 필터링해 만들었다.
- 미검사 제품이 최근 60건 밖으로 밀리면 데이터베이스에는 남아 있어도 화면에서 사라졌다.
- 화면에서도 대기열을 최대 6건으로 잘라 표시하고 있었다.

### 변경 내용

#### 백엔드

- `GET /inspection-queue` 전용 API를 추가했다.
- 최근 수신 목록의 조회 제한과 관계없이 `검사 대기`, `검사 중` 제품을 별도로 조회한다.
- 검사 중 제품을 먼저 표시하고, 같은 상태에서는 불량확률이 높은 순으로 정렬한다.
- 검사 완료 전까지 해당 제품은 활성 검사 대기열에 유지된다.

#### 프론트엔드

- 최근 예측 목록과 검사 대기열 상태를 분리했다.
- 검사 대기열은 `/inspection-queue` 응답을 사용한다.
- 기존 최대 6건 표시 제한을 제거했다.
- 전체 활성 대기열을 세로 스크롤로 확인할 수 있도록 변경했다.
- 대기열 건수는 최근 조회 결과 길이가 아니라 전체 `검사 대기 + 검사 중` 건수를 표시한다.
